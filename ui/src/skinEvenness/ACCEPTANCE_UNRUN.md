# Face chroma evenness: partial implementation, acceptance UNRUN

## Identity and bounded behaviour

- Exact reference: `LNX-REF-PC-32465-C-60b7c0e3d1`.
- Exact catalogue leaf: `PC-32465|AI肤色统一（脸部）` in `ui/src/spec/refine.json`.
- Visible product label: **脸部色度均匀（原片自参考）**. The official leaf remains **partial**, not complete or accepted.
- Official source verified by the coordinating task on 2026-10-24: https://www.pixcakeai.com/guide/32465, “AI肤色统一（脸部）”. Its description covers uneven face colour, red cheeks and special colour patches; it does not specify a numeric domain or algorithm. The narrower implementation does not establish full official, learned-AI or proprietary parity.
- Independent operation `lnx.skin_evenness.v1`, exactly `{version: 1, amount: 0..1}`. Display 0..100 is original local policy, not an official calibration. Zero is neutral for this new operation only. Nonzero values do not prove changed pixels or accepted photo quality.
- Uses measured same-face low-frequency chroma as its self-reference from the current effective RGB source, original or returned composite. The current stage receives the measured chroma correction while preserving its input linear luminance. Later effects may change luminance; this is not a guarantee for the final composed image.
- Not brightness, whitening, broad blur, global tint, colour temperature/tint, gloss, texture, clarity, a learned defect model, makeup recognition, physical lighting/material decomposition, body-colour unification or matching skin colour across people. Shared scopes share an amount, never a colour reference across faces. Makeup, coloured lighting and real pigment differences may be affected; the feature cannot know whether a difference should be removed.

## Legacy compatibility is explicit, not a migration

- The former exact-leaf alias to `skin.broad` is removed. The new leaf has a separately labeled legacy details section, preserving the old photograph-level strength and `broad_gain` controls; the old smoothing parameters remain photograph-level and use the skin mask, not the selected people scope.
- Legacy strength display 0..100 continues to send `strength / 100` through `commitSkin`. The compatibility broad slider displays its actual 0..2 range and sends the same `broad` value through `commitSkin` and `skinEditOptions`, retaining `broadGain`, the old command, rendering and serialization meaning. No values are copied into the new amount, migrated, cleared or rewritten on mount.
- Old strength 0 disables old smoothing. Old broad 0 is the historical default, **not neutral** and not a disable action. Double-click/reset still writes each old default; explicit reset buttons name these meanings. The new neutral button changes neither old parameter.
- Existing `dim` and `skinWhy` checks remain, and legacy compatibility controls are disabled while people requests are pending or uncertain. `commitSkin` also refuses pending/uncertain people mutations. The old command's unsupported derived-source refusal is unchanged; the new operation does not bypass it.
- Adjacent skin and lip controls retain their routes. The skinColour, skinFinish, skinGloss and skinTexture authored wiring fixtures now expect the intentional new leaf route and explicitly retain legacy-access assertions instead of enshrining the misleading old alias.

## Authority, source, intent and recovery

- `skin_evenness_available` / `skin_evenness_reason` only report dedicated core readiness. Real source/support/geometry/chroma admission remains engine-owned and per face. The UI never synthesizes mask or colour evidence or equates readiness with measured support.
- Selected-face resolved amount and authoritative provenance appear separately from explicit target amount. A shared target without valid explicit intent gets a blank deliberate choice, never the selected face's inherited value or implicit zero. Blank choices submit only via Apply, not on mount or blur.
- Nonzero changes require current source/document/face identity, analysis and state/association revisions, enabled verified analysis, dedicated readiness, valid target ownership and preview membership. Person links must be confirmed with a valid nonfuture confirmation revision. Resolved provenance must belong to the current source and face, including all contributing group/person targets.
- Missing, stale, conflicted, invalid or foreign authority is unknown, not neutral. A generic engine refusal remains labeled as a generic people refusal; the UI does not attribute another operation's failure solely to this feature.
- Disabled, pending, unknown-outcome, hair, white-balance, portrait competitors and edit-queue in-flight/pending/closed fences remain active. Owner callback identity/generation, mounted state, source/target/membership binding snapshots and a synchronous submission latch reject stale or duplicate dispatch. Confirmed fast failures release the latch through the owner state snapshot. Query errors from obsolete bindings are not shown.
- Standalone neutral recovery sends exactly one `/amount = 0` patch through the canonical people owner for the current target. It does not unset inheritance, reset old smoothing or adjacent operations, clear support, remove history or alter other scopes. With valid ownership and request fences, recovery does not need a selected preview, authoritative value, valid anatomy or available core. Other nonzero scopes may still cause engine refusal and are not automatically cleared.
- The existing people workflow retains command, receipt, queue, refresh, history, undo/replay, preview and export ownership. No alternate rendering, native command, optimistic graph or second preview is introduced. Unknown outcomes query the original request, never resend.
