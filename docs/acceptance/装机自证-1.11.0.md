## 1. 三项整改（对着原始指令逐条落）

### 1.1 画质：默认代理档 = 4K UHD（8 294 400 像素）

| 位置 | 改前 | 改后 | 守卫 |
|---|---|---|---|
| UI 导入预算 `maxPx` | 576 000 | **8 294 400** | `test_ui_dnd.py::test_product_ui_has_no_debug_surfaces_and_exactly_four_groups` |
| 引擎默认 `decode.PROXY_PIXELS` | 960×600 = 576 000 | **8 294 400** | `test_decode.py::test_default_proxy_budget_is_the_product_4k_tier` |
| 引擎上限 `decode.MAX_BUDGET` | 8 000 000（会把 UI 的 4K 档整条拒成“图打不开”） | **8 294 400** | `test_decode.py::test_proxy_budget_accepts_the_product_4k_tier` |

三处是同一个数，谁掉队都有用例报红：此前只有 UI 抬到 4K，引擎默认仍是 960×600，
任何不显式传 `max_px` 的入口（自动臂、工具、脚本）都会悄悄回到低清——那正是“大屏
上拉伸成马赛克”的根因。这一版把引擎默认本身改成产品档，而不是让调用方去记得传。

真窗口读数（装机件，4000×3000 的 4K 靶图，日志 `/tmp/m0-shot2.log`）：

| 项 | 读数 |
|---|---|
| 代理帧 | **3320×2488**（8 260 160 px ≤ 8 294 400） |
| 每帧字节 | **33 040 640 B**（RGBA） |
| 解码 | 121.12 ms（device `cuda`） |
| 导入总计 | 627.00 ms（含 scale 236.50 / first-frame 244.77） |
| 连续 `image_stream` 跑靶 | 5.04 fps / 83.3% drop（16.6 ms 强推一帧的合成压力，不是按需编辑帧率；本轮为软件合成，硬件合成上一轮同图是 5.60 fps / 80%） |
| 1024×1280 夹具 | 原幅不缩：`"notes":["源图已在代理档以内，未缩放"]` |

代价账写在这里，不藏：4K 档双缓冲 **66 MB** tmpfs，引擎 `bytes_bands` 396 MB；
按需编辑的渲染分位数见 §5（拖动 p95 0.40 ms）。这是“清晰优先”的选择，不是又把
fps 当门禁。

都是原幅解码/渲染，数字变大是“换了一张更清楚的纸”，不是退化。RAW 那一臂仍是合成
DNG（尺寸/位深/排阵形状对、传感器噪声结构不对），限制原样留在档的 `notes` 里。

## 6. 截图口径（为什么不是 `scrot` 直接抓）

WebKitGTK 的 GL 表面不落 X pixmap：真窗口用 `scrot`/`import` 抓客户区只会得到纯黑
（M2-a2 已证）。本档两张图的采集方式：

1. **真窗口**：以 `GDK_BACKEND=x11`、`WEBKIT_DISABLE_COMPOSITING_MODE=1` 启动装机壳
   （软件合成，内容才会落进 X 绘制面），用 `LRT_LOAD_IMAGE` 导入 1024×1280 夹具，
   `import -window <id>` 抓窗口。人物是仓库合成夹具，不是真实客片。
2. **空状态**：同一份前端源码的 Vite 预览，用 `google-chrome --headless=new
   --screenshot` 渲染（浏览器代理，无 Tauri 宿主；只用于看布局与配色）。
