# ADR-0015：眼牙增强只做"几何掩膜 + 相对内容门"的局部乘加，掩膜边界用精确求交

日期：2026-10-18　状态：已采纳（目标版本 1.8.0）
关联：《开发验收用例》LNX-PORTRAIT-009（P1·眼睛牙齿增强）、PORTRAIT-001/003/004（同一份
关键点与同一套作用人保护）、COLOR-004（局部作用域的先例）、DoD §2（严禁假滑块/伪装 AI）、
DoD §3（未接通功能显式禁用并说明原因）、DoD §4（逐项跑通 P0/P1）、ADR-0009（实测才能定档）、
ADR-0011（defer 与 invalidate 的分层）、ADR-0013（方向约定：能看见"生效"不等于没反）

## 1. 起因：这一格既不能是假滑块，也不能是"神经网络"

PORTRAIT-009 要的是眼白提亮 / 虹膜增强 / 牙齿美白。行业里两种做法这一条都不许用：

- **假滑块**：把整张图做一个全局曲线，再在 UI 上写"眼睛"。DoD §2 明确严禁。
- **伪装 AI**：接一个"眼神光/牙齿分割"模型。项目是纯开源离线产品，权重许可与体积都要过
  THIRD_PARTY_NOTICES 那一关；而这一格的物理需求（在既定解剖区域内做有限的亮/艳调整）
  用 MediaPipe FaceMesh 已有的 478 点就能精确框出来，多一个模型只是多一个能坏的东西。

所以这一层的定义收敛成一句话：**掩膜从关键点几何画，效果只在掩膜内做逐点乘加，
每一格能不能用由"源片那一片到底像不像眼白/牙齿"说了算，不像就整格不点火并写明原因。**

## 2. 决定

### 2.1 三条构造性质（不是调参调出来的，是算式的形状）

1. **色相那条轴一次都不进**：子效只改 s（乘性）与 v（乘性后夹天花板）。中性像素
   `s=0` 时 `0×(1+k)=0` 恒等于 0，**结构上不可能被上色**——"灰眼睛突然变蓝"这种
   靠调参加防的错，在这里没有来源。
2. **只许往上推，不许拉暗**：`v' = min(v·(1+k·a·w), max(v, V_CEIL))`。写成
   `_cap_up(y, x, ceil) = min(y, max(x, ceil))` 而不是 `min(y, ceil)`：后者在
   `x > ceil`（本来就比天花板亮）时会把用户的像素**往下拽**，在牙齿上留一块比原片更暗的
   高光，比过曝更难查。于是两条判据在数学上恒成立：`v' ≥ v`（实测三夹具
   `darkened_px = 0`）、原本 255 的格不会被新挤出 255（`new_clipped_px = 0`）。
3. **混合写成 `x + (out − x)·wc`**：`wc = 0` 处它在 IEEE 下精确回到 `x`（`0×有限 = 0`），
   所以"掩膜外逐字节不变"不依赖任何浮点巧合。三夹具实测**窗口外改动格数 0**。

### 2.2 掩膜边界：极坐标线性插值是**外偏**，改成逐射线—边段精确求交

第一版 `_star_weight` 与 `_star_ok` 共用"按角度找相邻两顶点、半径线性插值"的写法。
写测试时拿一个解析正方形对拍，**框外 420 个格点拿到了满额度**。定性为真缺陷而不是
测试写错：对一条直边，两顶点半径的线性插值给出的是 `r·1/cos(Δθ/2)`，恒**大于**弦的真实
距离——Δθ=22.5°（16 点眼环的常见张角）外偏 1.9%，Δθ=45° 外偏 8.2%，Δθ=90°（正方形）
外偏 **41.4%**。模块注释里原来那句"约 0.8% 内偏"方向整个是反的，一并更正。

决定：权重场的半径改为**逐射线与该边段的精确求交**，与 `_star_ok` 用同一套克莱默解与
同一套退化处理（`|det| < 1e-12` 退化成顶点距离；交点在射线反方向记 0，不画假凸起）。
代价是每帧一次几百微秒的矢量批处理，只在 build 时做一次；换来的是"多边形外恒 0"这个
可以拿解析图形对拍的性质，以及 `test_star_weight_is_exact_against_a_winding_number_reference`
（8 张随机星形 vs 绕数参考解，外扩/内缩双向判）能长期当门神。

### 2.3 窗口：先算 feather，后定 pad

`_star_weight` 在 `rb + feather/2` 处归零，所以软边必须整个落在窗口里。原来的固定
`REGION_PAD_PX = 6.0` 兜不住唇环 feather（`0.05 × 嘴宽`，1024 宽夹具上实测 ≈15 px），
嘴角的软边被窗口边界**硬切一刀**——画面上是一圈生硬的唇线，而逐字节判据看不出来
（切在窗口边界外，"窗口外不动"依然成立）。改成：feather 具名为 `EYE_FEATHER_OF_IRIS`
/ `LIP_FEATHER_OF_MOUTH_W`，先算出实际 feather，再取
`pad = max(REGION_PAD_PX, 0.5·max(feather) + 1)`；并加一条能负向自证的用例
`test_window_contains_the_whole_soft_edge_of_every_region`（先红后绿）。

### 2.4 混合权重只统计**点火了**的子层

`wc = clip(w0+w1+w2)` 看着无害，但它把 hsv↔rgb 往返的 1e-17 舍入也混进了画面：
只开牙齿时实测有 **114347 格眼白像素**与源片差 1e-17。8-bit 预览上看不见，
16-bit 直通导出上就是一次真实改动——而"每子功能独立启停"要的正是逐字节。改成
只累加 `amount > 0` 的那几格（numpy 与 torch 两臂同式）。

### 2.5 内容门用**相对本池均值**，不用绝对阈值

绝对阈值（比如"v > 0.7 才算眼白"）在深肤色与低光上必然失灵。三个门都以**被检区域自己
的均值**为基准（`_pool_mean` 拿权重场加权），并留软边（`*_SPAN` 是 ramps 的宽度）：

| 门 | 判据（相对基准） | 实测作用 |
|---|---|---|
| 眼白 | `s ≤ 0.62 × 虹膜盘饱和均值`，且 `v ≥ 0.86 × 眼白自身均值` | 露齿夹具拦掉 751 格（睫毛/眼线）；**眼镜夹具拦掉 1528 格**（镜框横梁与镜片边） |
| 虹膜 | `s ≥ 0.24 × 盘面均值`（下界门） | 镜面高光、镜片反光不进：眼镜夹具拦掉 1488 格 |
| 牙齿 | `s ≤ 0.72 × 口腔内容均值` 且 `v ≥ 1.06 × 该均值`，门后不足 12 格整格不点火 | 几何唇环区 15561 格 → 门后 5361 格：口腔内壁、唾液反光、唇面被掉 |
| 嘴开度 | `lip_gap / 嘴宽 ≥ 0.055`，闭嘴直接拒并写原因 | 闭嘴样本的牙齿那一格 `gated_px = 0` 且 reason 说得出"闭嘴" |
| 虹膜半径 | `≥ 1.0 px`，小过一档拒（远脸/侧脸） | 两只眼都被拒时眼白整层不点火（没有基准就不硬造一个） |

**基准缺失就不点火，而不是退化成绝对阈值**：拿"随便一个数"顶上，就是把不可信的一层
伪装成可用——正是 DoD 严禁的那一类。

### 2.6 事件只有一个组装点，平铺与嵌套两份字段各归各的形

`enhance_done` 的图层字段只在 `vram._enhance_payload()` 组装，命令/重挂/放下三条臂共用；
`server._emit_enhance_state()` 只在其上叠平铺字段（`amounts/built/defer/lit/gated_px/
person_box/render_ms/total_ms`）。本轮为这个形状付了两次学费：

- 接线时把 `info` 按**位置**传进只接受关键字的签名 → 第一条 enhance 命令就 TypeError，
  而库层 41 条完全盖不到（它不走 server）。教训：命令签名改动必须有一条端到端兜着。
- 平铺 `reason` 是**整层**一句话（defer/invalidate 才有），而 `doc_state.enhance.reason`
  是**逐子功能映射**——同名不同形。UI 的 `reason[sub]` 落在字符串上取下标恒 undefined，
  "禁用必须带原因"这一句在屏幕上就读不到。现在 TS 侧两形分开（`EnhanceInfo extends
  Omit<EnhanceDoc, "reason">` + `enhance_reason`），在 `enhanceStateOf()` 一处归一。

### 2.7 defer / invalidate / SCOPE-001 沿用形变层那一课

关键点不随工程走 → 重开工程时 `defer`（参数存住、不进画面、自动补分析后 rebuild）；
synthetic 模板几何、认不回脸盒、重画失败 → `invalidate` + `dropped_amounts`（UI 不许把
滑块弹回 0 之后又说"已生效"）。多人图未点选 → 整层拒（`blocked`），因为这一层的掩膜
必须知道画在谁的虹膜上，**不拿 A 的参数去服务 B**。

### 2.8 预览与导出是同一份几何的重放

导出按**导出尺寸**从 `spec.landmarks` 重画掩膜，分块时逐块
`set_enhance_field(window, weight, origin=(cy0, cx0))` 与本块求交；完全在块外的块
**整层不挂**（`has_enhance()` 如实 false），而不是贴一张空场。这样"屏幕上眼睛被画到
下巴上"这种错在结构上进不来，而端到端判据是"导出图上窗口内动、窗口外逐字节"。

### 2.9 两条计账纪律（都是定版这一轮撞出来的）

1. **事件里的耗时账要取在渲染之后**。`cmd_enhance` 原来是"组装 info → 出帧 → 发事件"，
   于是第一条命令报出的 `enhance_ms` 恒为 0——那一刻这一层还没进过帧通路。恒 0 的计时
   比没有计时更坏：它把"没量到"报成"量到了 0"，而 m5 第 8 臂的 `0 < enhance_ms` 判据
   正好被它变成假红（本轮真撞了一次）。改成与 `cmd_deform` 同一次序：**先出帧，后组装
   那一帧的账**。
2. **"这一层多少钱"以性能台账为准，不以真窗口那一格为准**。`apply_enhance` 里的
   `torch.cuda.synchronize()` 等到的是这块卡上排到此处为止的全部工作；真窗口里同进程
   还有帧通路在跑靶，本轮量到 54.9 ms 一档，而隔离量是 **1.15 ms p50 / 1.37 ms max**
   （见 `docs/acceptance/性能分位数-1.8.0.json` 的 `enhance_apply_ms`，与形变那一层的
   1.09 ms 同一档）。把前者当这一层的
   成本就是假指标，所以台账里新增一臂，与 `deform_apply_ms` 同一个分法：
   `enhance_build_ms`（一次性重画掩膜）与 `enhance_apply_ms`（拖动期间每帧逐点乘加）分开记。

顺带定一条功能事实：**拖滑块不许重画掩膜**。原来每次非零 set 都调 `build_enhance`
（几何栅格化 + 内容门 + 一次 D2H，实测 12–22 ms/事件），与这一层"系数与几何各算一次钱"
的设计相反。现在按关键点指纹复用场（`enhance_needs_rebuild`），性能臂把
`enhance_rebuilds_during_drag == 0` 钉成回归判据——与 `deform_builds_during_drag` 同一个身份。

## 4. 判据落点

- 库层：`engine/tests/test_enhance.py` 41 条（两臂对拍、精确求交 vs 绕数参考、窗口含软边、
  牙齿掩膜落在夹具画的牙上、逐子功能独立启停、内容门与拒绝原因、非有限值整层拒）。
- 端到端：`engine/tests/test_acceptance_p1.py` 两条（逐字节八段 + 拒绝/defer/重开工程/
  多人保护那一段），验收执行器映射 `LNX-PORTRAIT-009` → P1 12/17。
- 真窗口：`packaging/m5-release-check.sh` 第 8 臂（露齿夹具单独一个窗口），判据是
  三个数原样递到引擎、每格"要么有覆盖格要么有原因"、`insideChanged > 0`、
  `outsideChanged == 0`、`backHomeBytes == 0`、`device == 本机 torch 真认的那块`。

## 5. 显式不做

- **负档**：AMOUNT_LIMIT=1.0 且值域 [0,1]。"反向的眼白提亮"（提暗/加黄）没有可信的
  解剖依据，也不在验收用例里；留一个反向滑块就是假能力。
- **不做眼神光/瞳孔放大/牙龈整形**：那些要新的几何与新的门，属于别的用例条目。
- **不用任何学习式分割**：这一层的可信度全部来自 478 点几何与源像素的颜色统计。

## 6. 后果

- 好的一面：这一层的每一条 then 都能被**解析图形**或**逐字节**证明，不依赖观感评审；
  反假滑块的那一句由"门后格数 + 出片 ΔLSB"两格数字承担。
- 代价：每次**关键点变化**都要重画掩膜（实测 `enhance_build_ms` = 21.87 ms @ 产品档代理，
  只在几何变了的时候付一次）；拖动期间每帧逐点乘加 `enhance_apply_ms` = 1.15 ms p50 /
  1.37 ms max（n=60，device=cuda），且 `enhance_rebuilds_during_drag = 0`；
  导出分块要多切一次场。这几个数落在 `docs/acceptance/性能分位数-1.8.0.json`。
- 风险与守卫：内容门阈值是在三份夹具上标的，不是全局最优。因此"没接通必须带原因"
  是硬要求——真机上遇到认不出的眼睛，用户会看到为什么，而不是看到一个不动的滑块。
