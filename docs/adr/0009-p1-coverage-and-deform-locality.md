# ADR-0009：P1 的覆盖边界、形变的局部性半径与两处测试形状错误

日期：2026-10-18　状态：已采纳
关联：《开发验收用例》MANUAL-001/002/003、RAW-001、PORTRAIT-007（以及未覆盖的
PORTRAIT-003/004/005/006/008/009/010/011/012、COLOR-004、BACKGROUND-001、PICK-001）；
ADR-0003（质量阈值）、ADR-0008（模块作用域与肤质阈值）

## 1. DoD 要跑 P0/P1，而"跑通 P1"不等于"给 P1 全签字"

`docs/acceptance/case-map.json` 现在的账是：**P0 57/57 有测试引用，P1 5/17，P2 0/6**。
本轮新增的那 5 条都在 `engine/tests/test_acceptance_p1.py`：MANUAL-001、MANUAL-002、
MANUAL-003、RAW-001、PORTRAIT-007（末条自动化那半 + `manual` 标记）。

剩下 12 条 P1 **没有测试**，报告里是 `uncovered`，每条在映射里带一句真实原因：

- PORTRAIT-003/004/005/006 需要"人物身份模型"（按人分层、覆盖继承、跨图同一人、
  人工纠正优先）。本版本的配方是**文档级**的，多人照片走的是 SCOPE-001 的整条明拒。
- PORTRAIT-008/009/010/011/012（全身、眼牙、妆容头发、手脚、表情）零实现。
  FaceMesh 的 478 点不含手脚，也没有妆容/表情的独立效果层。
- COLOR-004 / BACKGROUND-001：只有笔迹层与 `skin`/`bg` 通道，"指定区域调色"与
  "背景/衣物效果"作为独立可撤销层没接通——**没有效果就没有可判的像素差**。
- PICK-001（AI 挑图）：要做它就得引入一个我们没有的分类器。用阈值规则冒充"AI 判定"
  正是 DoD §2 明令禁止的事。**宁可留未覆盖，也不签一个假实现。**

这不是"少写测试"：`tools/run-acceptance.py` 对 `uncovered` 单独计数并在报告里标红，
且 P0 有一条都没放过；P1 的 0 覆盖会被写进汇总而不是被隐去。

## 2. 形变的"紧支撑"承诺到哪一步：过渡带内会带动背景，这是物理不是缺陷

PORTRAIT-007 第一版判据我写的是"图像外沿 4px 必须逐字节为 0"。实测**响**：
`slim_face=0.2` 时左边缘最大 10 LSB。探针（同一张图、只改形变量）把它定性了：

| slim_face | 左 1 列 max | 左 4 列 max | 左 4 列 >2LSB 格数 | 全场 >2LSB 格数 |
|---|---|---|---|---|
| 0.01 | 0 | 1 | 0 | 4 296 |
| 0.10 | 1 | 5 | 35 | 57 276 |
| 0.40 | 3 | 15 | 220 | 79 267 |
| 0.80 | 7 | 26 | 345 | 88 410 |

**随形变量线性增长**（而 `deform clear` 之后逐字节回 0）——所以那不是重采样噪声，
是形变场在左边缘真的有非零值。查实现：`ops/deform.py` 的窗是各向同性紧支撑圆
（`FLAT_RATIO=1.05`、`SUPPORT_RATIO=1.60`，半径以"脸半对角 R"为单位），而这张
400×504 的图上左边缘正好落在 **1.48R**，在 1.05R–1.60R 的过渡带里（窗还开着约 12%）。
顶/底与右列量到 0 是因为那几处是均匀背景，位移不产生 LSB 差——**同一件事在有无
细节的地方读数完全不同，这也是为什么"外沿"不是个好判据**。

决定：**不为了绿而把过渡带压窄**。`SUPPORT_RATIO` 从 1.60 降到 1.4 以下确实能让
边缘读数为 0，代价是把同样的峰值位移挤进更窄的环带（smoothstep 的一阶导变大），
真实照片上会看见一圈"糊/皱"的环——那是更难看、更难解释的缺陷。文件里还留着上一版
为削峰付过的账（旧值 1.35/0.62 让窗把请求的位移自己削掉 13.4px）。

判据因此改成引擎自己承诺的那条不变量，并且**数从引擎取**：`deform_done.build
.kinds.slim_face.window = [cx, cy, R, r0, r1]`，测试用 `r > 1.02·r1` 那片区域断言
**逐字节为 0**（紧支撑之外背景一动不动），配合"角上背景 0 LSB""面积 ≤60% 画幅且随
形变量单调""邻域跳变 ≤ 原图 + 40 LSB"。过渡带以内会带动背景这一事实连同上表写进本
ADR，而不是留成 UI 上一句"背景不动"的谎。

**人工那一半仍然没签**：用例原文最后一句是"背景异常纳入人工审核"，`case-map.json`
把 PORTRAIT-007 标了 `manual: true`，报告状态是 `manual_pending`。

## 3. 本轮两处测试形状错误（都是"判据不成立"而不是"产品不成立"）

① **跨半径比包围盒**：MANUAL-001 的裁剪缩放比先拿 `radius=24` 的包围盒去比 `radius=60`
的裁剪态，读出 3.15×（期望 2×）而判成"笔迹按屏幕坐标成立"。带限半径作用在几何层**之前**，
基准必须同半径。改成拿 `box_wide` 作参照后 2.0× 通过。

② **`wait_for()` 会吃掉它路过的每一帧**：MANUAL-002 / PORTRAIT-007 都在 `precompute`
之后才去"读当前帧"，而 `wait_for("precompute_ready")` 把 load 那一帧一并消费掉，
于是 30s 超时——报的是"没等到事件"，实际是"这一帧根本不会再发第二次"。修法是**先取
基准帧再发 precompute**。同一条教训用在 deform 账单上：`_wait_frame_mode()` 只认帧，
`deform_done` 排在前面会被吃掉，所以新写了 `_deform_shot()` 一次收下【账单 + 那一帧】。

这两处的共同形状是：**测试自造的时序问题看起来像产品缺陷**。区别办法只有一个——
先问"这一帧是谁发的、还会不会再发"，再改判据。

## 4. RAW-001 的三段判据取自 decode.py 已有的分界

`has_preview`（文件里有没有预览）与 `used_preview`（这一帧是不是预览）在 decode 层
就是两个字段，`source` 三个值（`self_dng` / `libraw` / `libraw_preview`）；
`allow_preview` 默认 False，全仓只有缩略图那一处显式打开。测试把这句话变成判据：
编辑会话必须 `used_preview is False` 且 `source` 有名字，坏容器（JPEG 改名 `.cr3`）
必须**报错且之后不再发帧**——"报错归报错、画面照样给"就是静默换了渲染路径。

## 5. 后果

- `engine/tests/test_acceptance_p1.py` 5 条，运行时 venv 实测 22.4s 全过；全量回归
  797 passed / 7 skipped（本轮 +5）。
- 未覆盖的 12 条 P1 与 6 条 P2 在映射里各带一句原因，`map --write` 会保留 `note`；
  报告逐条表格里直接可见，不用翻代码。
- 记入本 ADR 的"过渡带内会带动背景"是**已知行为**：将来有人改 `SUPPORT_RATIO` 或
  加"背景保护"时，这张表和这条决定是起点，不能重新当成新发现。
