# ADR-0006：项目持久化——单文件 JSON + 原子替换，而不是 SQLite

日期：2026-10-18
状态：已采纳
相关：ADR-0003（质量阈值）、ADR-0005（裁剪是文档状态的一部分）、
《P0参数注册表.json》`lnx.project.v1`（create/open/save）、
《开发验收用例.json》CORE-001 / CORE-007 / CORE-008 / P0-*-NEUTRAL（"保存重开"）

## 背景

注册表里 `lnx.project.v1` 的三个 parameter_key 是 **action**（create / open / save），
而 80 条验收用例里有 6 条直接或间接要求"重开"：

* CORE-001：创建项目、导入、关闭并重新打开 → 照片集合、标签、活动版本和配方完整恢复；
  **源文件哈希不变**；
* CORE-007：移入回收站再恢复 → 项目记录可恢复，**原图不删除**，配方仍在；
* CORE-008：自动保存事务执行中注入进程终止并重开 → 恢复到**完整旧版本或完整新版本**，
  没有半个配方或损坏数据库；
* P0-EXPOSURE / P0-WHITE_BALANCE / P0-CROP 的 NEUTRAL 三条，when 里都写着
  "应用中性操作、**保存、重开**、准确预览并导出"。

也就是说：d2a/d2b/d2c 交付的那些层，在没有持久化之前，其 P0 验收永远跑不完。
这一层不是"工程管理器锦上添花"，是那些用例的前置。

## 决策

### 1. 一份项目 = 一个 JSON 文件；写路径是 临时文件 → fsync → `os.replace` → 目录 fsync

不用 SQLite 的理由（按重要性排）：

1. **CORE-008 要的保证是 `os.replace` 天然给的**：同目录同文件系统上的 rename 是
   原子的，崩溃点只可能留下旧文件或新文件，不存在第三种。SQLite 要给同样的保证得管
   journal/WAL、锁与损坏恢复——那是多出来的依赖与多出来的可失败面。
2. 写的频率是"每次保存一次"，不是"每秒一千次事务"。数据库引擎在这里是纯成本。
3. 依赖最干净、零新依赖，符合"纯开源、离线可用"的产品定位。
4. **出问题人能直接 `cat` 那个文件**：离线普惠产品的自检门槛应当是"看得见的字节"，
   不是"需要一个客户端才读得懂的库"。这条已落成用例
   `test_saved_file_is_plain_json_a_human_can_read`（断言非 ASCII 不转义、有缩进）。
5. 便携：项目文件跟着照片走，拷走就是整个工程。

代价也写清楚：整份文档在内存里编一次 JSON，所以**不适合大到几百张带自定义调色表**。
上限写死在 `MAX_ASSET_BYTES` / `MAX_PROJECT_BYTES`，超限的资产**丢弃并逐条记原因**
（`dropped` 里带 `at` 路径），不当场崩、也不假装存进去了——"未接通显式禁用并说明
原因"这条产品纪律同样适用于持久层。

### 2. 配方的序列化：内容寻址资产，而不是把张量塞进 JSON

`_capture_state()` 里有 numpy 数组（画笔覆盖度、换底遮罩、调色表原件）。编码规则：

* uint8 且形状是 `(H,W)` / `(H,W,1)` / `(H,W,3)` / `(H,W,4)` → **PNG 无损**；
* 其余数组 → raw 字节 + shape + dtype；
* 资产按 sha256 去重：二十张图共用一张表，文件里只有一份；
* dataclass（RepairOp/LightOp）→ `{"__dc__": 类名, "fields": {...}}`，解码时类由
  **调用方注入**（`dc_types`）。持久层不 import 计算模块：反向依赖会形成循环，而且
  会让"读一个 JSON"这件事取决于 torch 在不在。

上限卡的是**编后写进文件的字节**，不是数组原始字节。这条方向错过一次：拿 `nbytes`
当判据会把"原始 12 MB、PNG 后几百 KB"的换底遮罩误杀，而那正是"保存成功而下次打开
少了一半配方"。现在 8 MB 上限两侧各有一个形状在用例里（3000×3000 噪点必拒、
4000×3000 遮罩必收）。

`NaN` 一类不可表示的数：encode 记进 `dropped` 并置 `None`，`json.dumps` 又用
`allow_nan=False` 兜底 —— 默认行为会把 `NaN` 写成非法字面量，**当场编得出来、文件
也在、下次打开才炸**，那正是"半个配方"的形状。

### 3. 指纹分两等，`hash_level` 明写手里是哪一等

* `full=True`：整文件 sha256 —— CORE-001 的"源文件哈希不变"要的是这一等；
* `full=False`：头部 4 KB + 长度 + mtime —— 扫描 512 张时逐张全文件哈希会把导入拖成
  几十秒，而导入那一层只要能认出"文件变了 / 被换了"。

本机量到的数：0.41 MB 样张 warm 1.0 ms、0.03 MB 合成 DNG 0.2 ms（≈ 2.4 ms/MB）；
25 MB 真机 DNG 按这一条**推**是 ≈ 60 ms —— 本仓没有 25 MB 样张，注释里明写哪个是
量出来的、哪个是推出来的。

写这一等时真出过一个错：head 快路径把"剩下的块数"加进了 `n`，2.5 MB 的文件报成
1,048,578 字节。`verify_fingerprint` 拿这个数判"图被动过没动过"，**错的方向是"变了
说成没变"** —— 最不该错的那一侧。反向门禁已实测：把那段快路径贴回副本跑新用例，
head 那等确实响，full 不受影响，所以新用例两等都跑。

### 4. 回收站是项目记录，不是对原图动手

`set_trashed` 只置标志位：不 `unlink`、不改 mtime、配方原样留着。CORE-007 的 then
逐字对应："项目记录可恢复；原图不删除；配方仍在"。

### 5. 校验的形状与"坏一张不许锁整个工程"

`validate()` 校顶层键、schema_version、docs 是列表、path 不重复、versions 是列表、
`active_version` 键存在。而"活动版本指向不存在的版本"这一格**留到 `active_recipe()`
逐张响**：一张图坏了不该把整个工程里几百张图一起锁在外面。损坏文件报成"损坏"，
不是笼统一句"打不开"——那是两种处置。

### 6. 同名的两个项目不互相顶掉

`project_path_for` 递编号（`婚礼` → `婚礼-2`），不拿时间戳当后缀：那会造出一堆名字
看不出差别的文件，而用户要在工程列表里认出它们。这是 EXPORT-001 那条"无提示覆盖"
发生在工程层的预防。

## 本轮未做（下一步的输入，不是"以后再说"）

* **`cmd_project` 接线**：create / open / save / state / tag / trash。持久层现在只有
  纯函数与文件 IO，事件与线程仍按老规矩在 server 那侧。接线时要处理：
  `_apply_state` 对 list→tuple 的还原（`_grade/_exposure/_crop_rect`）、`_proxy` 档
  不一致时按 `_drop_proxy_layers` 作废逐点层、以及"保存时补算缺失的全文件指纹并把
  这一段耗时报出来"（不把它藏在 load_image 的首帧里）。
* **版本的取舍**：`versions` 支持多格已实现（`add_doc` 每次追加、`put_active_version`
  按 id 切）。会话里的 undo 栈**不随项目落盘**——一百步 × 每步的笔迹遮罩会把工程文件
  撑成照片备份。撤销历史是会话态，命名版本才是项目态；这条边界要在 server 接线时写成
  事件字段（`saved_versions` / `session_only`），让 UI 能显式说明而不是留个空列表。
* **`task` 那一层（TASK-001/002/003/004/006/007/008/009）**：批量队列的
  pause/resume/cancel/retry 与"提交期不许被暂停打断"。引擎里现在一条都没有。

## 证据

`engine/tests/test_project.py` 29 条（往返、原子性注入、NaN、截断损坏、校验形状、
PNG/raw 逐字节、去重、上限两侧、未知类型留原因、数据类双向、资产哈希与形状被改、
命名不冲突、指纹两等与跨块长度、verify 三种"不对"、源文件只读、纯 JSON 可读）。
运行时 venv 定向 42 passed；开发 venv 413 passed / 261 skipped。
