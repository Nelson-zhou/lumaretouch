# ADR-0010：局部调色的作用域语义、导出同口径与一次被守卫抓住的自伤

日期：2026-10-18　状态：已采纳（1.3.0）
关联：《开发验收用例》COLOR-004（P1·局部调色）、ADR-0009 §1（本条此前记为未覆盖）、
ADR-0003（质量阈值）、ADR-0005（几何层的坐标归属）、M3-b（肤色定向层原始设计）

## 1. 要解决的问题

COLOR-004 的 `given/when/then` 原文：人脸边界与背景形成高反差的样本 → **仅对指定局部区域调色**
→ 「蒙版外变化在定义边缘范围内；撤销恢复；无明显色边」。此前肤色定向层（`ops/grade.py` 的
逐帧内核 + `vram.apply_grade`）只能全图：三个滑块与混入比例都作用于每一格像素。

三条路摆在面前，各自的代价不同：

1. **复用修容/减淡那套笔迹层**（`LightOp` 带权重、走 db 场）——最快，但那是亮度层，
   做不出色相/饱和定向，等于用"看起来像局部"冒充"这一层真的是局部"。
2. **在导出与预览各写一份"区域内调色"**——两份实现必然漂（本仓在 `_rehang_precompute`
   那一段写过同样的教训）。
3. **给定向层加一份"调谁"的状态**（作用域 + 区域），预览与导出共用同一个库层入口。

选了 3。理由：COLOR-004 判的是**同一条调色**被限制在区域内，而不是"再有一种局部效果"。
只有把作用域挂在定向层自己身上，"屏上看到的局部"与"文件里的局部"才是同一份数。

## 2. 决定

### 2.1 作用域名单只有一个出处，且在模块层

`vram.GRADE_SCOPES = ("all", "skin", "brush")` 放在 vram **模块层**而不是类里：命令层收到
一条 `grade scope=…` 时还没有可活的会话，"这个作用域存不存在"必须先能回答；而 `grade_done`
事件与 `doc_state.grade.scopes` 报的是同一份名单。写两处就是下一轮加第四档时漏改的那一处。

### 2.2 `all` 是真短路，不是"乘一个全 1 的掩膜"

`apply_grade` 的混合写成 `mix_masked(t, out, 1.0, w)`：w=0 时 `(1-0)·t + 0·out` 在 IEEE 里
就是 t 本身，所以"蒙版外逐字节恒等"**无条件成立**（`ops/guided.py` 里 mix_masked 的原始
论证同一条）。而 `scope=all` 走的是 `weight is None` 那条结构性短路——不拿浮点巧合当承诺，
也不给每帧多塞一遍逐点乘加。**"scope=all 与 1.2.0 逐字节相同"由测试钉死**
（`test_scope_all_is_byte_identical_to_the_pre_color_004_behaviour`）。

### 2.3 拿不到底衬就整条拒，不静默退回全图

`skin` 要人脸掩膜（还得真有 `skin` 那一格），`brush` 要用户画出的区域。任一样缺失时
`set_grade_scope` 抛 `ValueError`，命令层发 `error` 事件，会话原样未动。

这条不是洁癖：局部调色静默变成全图调色，**画面确实在变**，用户从屏幕上分不出来，而他会
以为只动了皮肤。与消除笔的 lama 守卫、birefnet 不许退色键、realesrgan 不许退 Lanczos
是同一条规矩的第四次落地。

### 2.4 区域随代理档作废，作用域与它成对作废

`_grade_mask` 是代理帧像素坐标 → 进 `PROXY_BOUND`；`_grade_scope` 也进去，因为
"brush/skin 而底衬没了"是每帧一异常的形状。`_fresh_doc_state`/`_capture_state`/
`doc_state`/`_hist_sig` 四处名单同步加了两格（这一族漏一处就是 d3b 那个 `load_image`
KeyError，名单守卫会当场响）。

重挂只有一个入口 `_rehang_grade_scope(replayed_for=…)`：`_attach_pipeline` 末尾调一次
（brush 当场能挂，skin 因掩膜还没上而**被推迟**），`_rehang_precompute` 成功后再调一次
（掩膜刚上，这才是 skin 能落地的时刻）。失败分支成对放下：库层 `clear_face()` 里也把
`skin` 退回 `all`，宿主字段由 `_drop_grade_scope` 退回并 `engine_warn` 说清。

`clear_grade()` **不动区域**（滑块归零不该抹掉用户涂的笔迹），`clear_grade_mask()` 才清区域，
并且顺手把 `brush` 退回 `all`。

### 2.5 落笔即生效

`grade action=mask` 在区域真非空时自己把作用域切到 `brush`，最终作用域随 `grade_done`
报出去（UI 的选择框读事件，不记第二份）。理由：涂了一笔而画面不动，是这一仓最像 bug 的
体验；而"先涂再切档"两步里用户没有任何提示说要切。显式的作用域下拉仍然在，用来**退回**
全图或换 skin。

### 2.6 出片同口径：带不上区域就把整层调色放下

导出跑在另一张网格上（满幅），所以区域走与修容笔迹同一条 `resample_field(..., uint8=True)`
双线性重采样；`ExportSpec` 新增 `grade_scope/grade_mask`，每个 tile 用**与补丁完全相同的
窗口**切一份（调色是逐点的，margin 里那些像素不参与它，所以不需要外扩）。

三种拿不到那一片的局面（旧批次台账、非当前文档、掩膜缺失）一律 **整层调色不带** 并逐图
写进 `skipped`：把局部调色搬成全局调色不是"批量应用设置"，而是一张错图。`ExportSpec.check()`
里那条"局部作用域 + 点火的定向必须带非空区域"是不许静默加宽的最后一道闸。

一个记账口径的变化：`grade_resident_bytes()` 以前恒为 0（这层不持有张量），现在 brush
会常驻一份 `(1,1,H,W)` float（就是 H·W·4 B：512×400 那一档算得出 819 200 B，而那个等式
由 `test_brush_scope_resides_a_mask_and_clearing_it_releases_the_memory` 钉住）。报实数而不是报 0——"查过、
确实没占显存"才是那句话的内容，"不报"等于藏账。

## 3. 判据与它们的边界（不粉饰）

| 冻结件那句 | 落成的判据 | 边界 |
|---|---|---|
| 蒙版外变化在定义边缘范围内 | 差场包围盒落在笔迹框 + 羽化支撑（feather+2）内；四角背景带 0 LSB | 羽化支撑之外必须逐字节 0；支撑之内是过渡，本来就该动 |
| 撤销恢复 | 全局 `history undo` 那一帧与点火前那一帧**逐字节相同**，redo 再逐字节回来 | 走快照重放那条路（DOC_FIELDS + 会话重挂），不是参数回滚 |
| 无明显色边 | 差场相邻跳变 **严格小于** 整片变化峰值（硬阶跃等于峰值；振铃超过峰值） | 阶跃掩膜不经羽化时这一条会响，那是它该响 |

另有两条端到端"不许静默降级"（skin 无 precompute、brush 无区域）与 `scope=all` 恒等旧行为。
`given` 里"人脸边界与背景形成高反差"用的是本仓程序化人像夹具——本机没有可授权的真人照片，
所以真人皮肤结构那半仍未验（同 ADR-0008/0009 记过的那笔）。

## 4. 被显式禁用而不是假装接通的东西

- 「仅肤色」作用域在没有跑过面部分析时被禁用，并把引擎那句拒绝原因显示在选择框里
  （DoD §3：未接通显式禁用并说明原因，绝不留无响应控件）。
- 「清除区域」在 `mask_px == 0` 时禁用。
- 「局部调色」那一支笔**不**依赖关键点，所以它不被"没跑面部分析"连带禁用——接通了的功
  被错禁，与"没接通却看着能点"是同一类错。

## 5. 未做与下一步

- 区域没有"擦除笔"：`mode=replace` 是重画，`mask_clear` 是整片清。真要擦需要一份带符号的
  覆盖度合成（与修容的 ±场同构），本轮没做，也没假装有。
- `scope=skin` 的羽化/边缘扩展沿用 skin 掩膜自身那份（`face.skin_mask_np`），没有再加一层
  专门给调色用的软过渡。
- 局部调色不参与模块预设与批量同步的候选名单（`scope.py` 里它是文档级坐标数据，不是参数），
  这是定义而不是遗漏：搬过去就是一条错图。

## 6. 后果

- 验收账从 P1 5/17 变成 **6/17**（COLOR-004 有引用且真跑通）；P0 仍是 57/57。
- 版本号 1.3.0；brush 作用域多一笔显存账；代理档一变会丢用户涂的区域（换来的是绝不拿
  旧网格贴新图），这条会在 `engine_warn` 里明说。
- `grade_done` 事件多三格（`grade_scope / grade_scopes / mask_px`），协议侧的键集闭合守卫
  把它们钉成必存——少一格或多一格的实现都会在测试里响，而不是在 JSON 边界上漂。

## 7. 本轮三次自伤，以及抓住它们的那道守卫

诚实记三笔，因为它们都不是产品缺陷，而是**改错了东西**：

1. 一次编辑工具调用把 `test_protocol.py` 里 **5 行与本次改动无关的注释删掉了**——那些行是
   `# 验收用例引用：<用例 ID>`，即 `tools/run-acceptance.py` 唯一的映射来源。删掉的后果不是
   报错，而是**5 条 P0 用例从"有引用"掉成 0 引用**（报告会长成"P0 55/57"这种看上去像测试
   退化的假红）。抓到它的是 `map --write` 自己打的覆盖率行；修法是从 `git show HEAD` 里把
   原行取回插到函数体首行，再逐行核对 `git diff` 的每一条删除是否都是本次意图。
   **教训固化成一条：改完非 ASCII 文件必须回读 diff 的删除侧**——工具说"成功"不等于只动了
   你以为的那几行，而这一仓最贵的坑正是"看起来完全自洽的谎"。
2. 两处判据一开始写错在测试自己身上：一是拿"画面相邻跳变"当色边对照（那张合成图自带水平
   渐变与噪声，量出"羽化比硬边还陡 19 vs 15"这种反了的方向；改成量**差场**才问到了它该问
   的问题）；二是在点火之后才取对照帧（于是"蒙版外恒等"比的是"内外都不许变"，一条真能力
   被写成永远响的假判据）。两条都是先响、再回头读自己的判据到底在问什么。
3. 把①修好之后仍然报了一条假红：`docs/acceptance/case-map.json` 是一份 **committed 的派生物**，
   而 `run` 只校 `cases_sha256`（用例集换了没有）不校它是否与当前测试源码同源。于是一遍
   818 passed 的全绿，报告却说"P0 未跑通 2 条"——那两条的引用早在上一笔 `map --write` 里被
   删掉映射、后面补回了源码而忘了重写映射文件。错不在产品而在工具：派生物落后时
   报告会自己编红。这一条的代价不只是难看——它把真红混进一堆假红里，而 7 分钟的重跑会
   让人开始怀疑报告而不是怀疑代码。
   修法是把"同源"做成机制而不是习惯：`run` 跑测试前先 `sync_map_with_sources()`，有差就
   当场刷新写回文件并把变动 ID 响出来（既不当没看见，也不偷偷改）；另加 `report` 子命令重生成报告，
   这样"改报告版式"不再需要一个全量重跑去换一行文案（重跑会用机器繁忙时的新读数换掉刚量
   好的那一份，分位数就不干净了）。执行器自己的 8 条测试见
   `engine/tests/test_acceptance_tool.py`：落后必须被报出来、人工格（note/manual/extra）不能被
   刷新抹掉、junit 状态聚合往保守靠、committed 映射与源码**双向**同源。另外这里还有一次
   当场被自己守卫抓住的自伤：本文件初版在 docstring 里提了一嘴一条真实用例的 ID，
   `map --write` 立刻把这个工具测试文件加进了那条用例的证据链——一句解释性引用伪造出了
   一条不存在的覆盖。因此多一条 `test_this_file_cites_no_real_case_id`：验工具的测试不许
   成为产品用例的证据。
