# ADR-0012：挑图建议只做本地确定性度量（不伪装 AI），清晰度两格一起判，建议是旁注不是状态

日期：2026-10-18　状态：已采纳（目标版本 1.6.0）
关联：《开发验收用例》PICK-001（P1·AI 挑图）、《Linux开源人像修图产品指导手册》§AI挑图 与 2127 行
（「建议标签可解释且可覆盖；不自动永久删除；相似分组不是绝对重复判定」）、DoD §2（严禁假滑块/假滤镜/伪装 AI）、
ADR-0002（MediaPipe 内嵌后端）、ADR-0006（工程只存输入不存派生物）、ADR-0009（实测才能定档这条纪律）、
ADR-0011（同一份分析结果里的多人）

## 1. 要解决的问题

冻结件这条叫「AI 挑图」，`given` 是一组「重复 / 近似 / 闭眼 / 模糊但有保留价值」的照片，`then` 两句：
**建议必须可覆盖、不会自动永久删除照片**；**近似分组与判定原因可见**。

手册与官网把这一功能描述成训练出来的分类器（10 种场景、正脸偏好、闭眼识别、美学评分）。本仓：

- 没有任何一个这样的权重，也不打算为了凑一个功能名去下一份**不可审计**的模型（与 DoD「依赖最干净、离线可用」
  和「纯开源非商业」直接冲突：权重不可读、更新不可控、许可要单独追）；
- DoD §2 明令「严禁假滑块、假滤镜或**伪装 AI**」。把三条 if 改名叫"AI 智能挑图"就是伪装。

于是这条能力只剩一个诚实做法：**做能被任何人复算的测量**，并且把"它不是模型"这件事写在功能自己的说明里，
而不是等用户去猜。

第二个问题不是读冻结件读出来的，是标定台（`packaging/pick-calibrate.py`）量出来的：
**"糊"这个字在单一读数上是骗人的**。拉普拉斯方差的绝对值按对比度的平方走，一张整体压暗 0.35× 的好照片
（0.001417）比一张真糊的（0.005476）还低——只看绝对值，判据会把"曝光保守"报成"拍糊了"。这不是调阈值能
解决的：调高就漏掉真糊，调低就冤枉暗图。

## 2. 决定

### 2.1 四条判据，全部是测量；UI 上不出现「AI」这两个字

`engine/src/lumaretouch_engine/picks.py`（纯 numpy，不依赖 torch/PIL/mediapipe）：

| 要报的事 | 度量 | method 名（进事件） |
|---|---|---|
| 近似/重复 | 9×8 灰度相邻列梯度 → 64 位 dHash → 汉明距离并查集分组 | `dhash64-hamming` |
| 糊 | 绝对高频能量 **且** 相对自身对比度（见 2.2） | `clarity-lapvar-ratio` |
| 同批里更软 | 相对自身对比度 vs 批内中位数 | `clarity-ratio-vs-batch-median` |
| 欠曝/过曝 | Rec.601 luma 落在 ≤8 / ≥247 的**裁切**占比 | `luma-clipping` |
| 疑似闭眼 | FaceMesh 478 点：上下睑中点像素距离 / 内外眼角像素距离 | `facemesh-eye-aperture` |

每一格读数都带 `method / value / threshold`，用户与下一个人能按名字复算。档位名（弱/标准/强、重复/标准/相似）
由引擎 ready 报出去（`pick_sensitivities`、`pick_thresholds`、`pick_fingerprint`），宿主与前端一份都不抄。

产品面上一律叫「挑图建议」：手册那四条规则项一一对上，而名字里不出现做不到的那件事。

### 2.2 清晰度两格一起判，再加批内相对线与对比度下限

```
blur            ⇔ contrast ≥ CONTRAST_FLOOR 且 lapvar < BLUR_SENSITIVITY[档] 且 ratio < BLUR_RATIO_SENSITIVITY[档]
soft_vs_batch   ⇔ contrast ≥ CONTRAST_FLOOR 且 ratio < 批内中位数 × BLUR_REL_FACTOR[档]
flat            ⇔ contrast < CONTRAST_FLOOR → 「判据不适用」，既不写清晰也不写糊
```

全部锚点出自标定台（同一份夹具，`portrait-1024x1280.jpg`）：

| 变体 | lapvar（绝对） | ratio（相对） | 结论 |
|---|---|---|---|
| 真图 | 0.011579 | 0.2996 | 不标 |
| 轻糊 r=1.2 | 0.010145 | 0.2633 | 不标（不冤枉轻软） |
| 明显糊 r=3.0 | 0.005476 | 0.1444 | **标 blur** |
| 压暗 0.35× | 0.001417 | 0.2969 | 不标 ← 单看绝对值就会标 |
| 提亮 2.6× | 0.005151 | 0.1880 | 由曝光判据标 overexposed |
| 纯色平坦 | 0.000000 | 0.0000 | flat → 不适用 |
| 平坦+噪声 | 0.000009 | 20.0 | flat → 不适用（噪声把比值顶爆） |

为什么还要第三条（批内相对线）：**绝对值跨图不可比**。两张夹具的真图 ratio 分别是 0.2996 与 0.5177，
拿一根线去量它们必然冤枉其中一张。而挑图的真实场景就是"同一批连拍里那张虚的"。实测：
两人夹具真图 0.5177、糊 r=4.0 后 0.2319（lapvar 0.007738 仍在绝对线上方），中位数 0.5177 → 相对线
0.5177×0.55=0.2848 —— **只有相对线抓得到这一格**，所以它单独存在，并且只标 `soft`（"建议复核"），
不与 `blur` 混写。

### 2.3 眼睑量的是像素，不是归一化坐标

`eye_openness` 先把 478×2 归一化点乘回 `(w, h)` 再量距离。这条不是洁癖而是踩过的坑：直接用归一化值开
`hypot`，横向分母是宽、纵向分母是高，同一张脸在 1024×1280 上读 0.370、在 1570×950 上读 0.754 —— 差整整
一个 `H/W`。量纲错，不是小数位。

分母用**同一只眼自己的眼裂宽**，所以它与脸在画面里多大、离镜头多远无关；取两只眼（多人图再取所有脸）的
**最小值**，因为"被头发挡住一只"会把均值拉高，而要问的是"有没有一只明显没开"。点数不够 478 契约一律返
`None` → 那一格写 `eyes_unknown` 并带着为什么，**绝不退成「睁眼」**（不许静默降级）。

### 2.4 阈值只当「要不要复核」的标记，不当结论

夹具是程序化画出来的脸，眼裂比真人开得大：睁开 0.4599–0.4723，把眼裂涂平后重新检测读到 0.2279/0.2329。
公开 EAR 文献里真人闭眼 <0.15、睁眼 0.25–0.35。所以 `EYE_SENSITIVITY = {weak 0.120, standard 0.165,
strong 0.240}`：强档刚好把"画出来的闭眼替身"标出来，而**不取在替身与睁开那两组之间的空档里**——那会把
真人小眼睛全部标成复核。拿画出来的脸当真人阈值的定标依据是不诚实的，这句话写在代码注释里而不是只写在这里。

同一份标定台还留下一格**反面读数**，如实保留：两人夹具的脸 0 涂平后睁开比从 0.4642 变成 0.4723（**没降**）
——那个变体在这一张脸上没造出闭眼。它不进判据，只用来防止后来人误以为"涂平一定等于闭眼"。

### 2.5 检测尺度会给读数带几个百分点的抖动，用例钉的是同侧而不是相等

同一张涂平图：在 512 档（引擎挑图用的分析尺度）读到 0.21883，在满幅读到 0.22795，差约 4%。因此端到端用例
钉的是两条**能钉的**：两个尺度都落在阈值同侧；**同一个输入两次跑读数逐字节相同**（去掉逐段耗时）。
要求跨尺度相等就是把度量写成假精确。

### 2.6 建议是旁注：不进工程文件、不进撤销栈、不改源文件

- 写进 `row["pick"]`，随 `session_state.docs[].pick` 上报（与缩略图同一类派生物）。它是**算出来的**，
  不是用户画的 → 不随工程文件走（与 `_precompute` 同一条理由，`_project_build` 根本不会取这一格）；
- 不在 `EDIT_CMDS` 名单里 → 一次挑图不进撤销栈、不打工程脏标记。端到端用例把这条钉死：跑完前后 history
  账单逐字节相同。
- 这一层**没有删除能力**：`suggest()` 恒 `overridable=True`、`auto_deleted=False`、`auto_trashed=False`；
  `cmd_pick` 全路径只有读文件，没有任何 unlink/move/trash；回收站是工程记录（ADR-0006）。
- 已有用户标签/标记/回收站时 `overridden_by_user=True`，读数一个不少（压过 ≠ 抹掉），UI 上换灰底并把
  「以你的为准」写在 tooltip 第一行。

分组池 = 本次量的 + 本会话此前已量过的那些格的哈希（存在 `row["pick"].measures.dhash`）。这一条是端到端
用例真撞出来的：只重跑一张时它的"组内 3 张"会缩成"组内 1 张"，表现是**动一下别的滑块，徽章上的组数自己在
变**。范围也随原因一起报出（`scope.analyzed / scope.pooled`），不假装分组看的是整个磁盘目录。

### 2.7 后台线程的形状照缩略图，且跑靶期间整条拒

`_start_picks / _pick_loop` 复用 `_thumb_*` 那三件套的纪律：归属**看 path 不看 index**、写回前按 path 再认
一次格子（列表可能在半路上被第二次 scan 换掉）、每 N 张让一次 GIL（帧通路每秒要 60 次调度）、一张量不开只
坏自己那一格（`pick_failed`）不带到倒整批。两遍是必需的：近似组是全体哈希上的关系闭包，第 3 张的"组内第几名"
要等第 200 张量完才知道，所以第一遍发 `pick_progress`（读数），第二遍成组后发 `pick_item`（建议）。

跑靶进行中拒绝开挑图：两边都要解码与推理，同时跑的话**跑靶读数就不再属于那一条通路**。这一句写在拒绝文案里，
而不是悄悄并行。

### 2.8 RAW 用相机内嵌预览，但必须写明来路

挑图是一次过几百张的浏览判断，用 `load_rgb(..., allow_preview=True)` 取半幅/预览（与底片条同一个开关）。
`decode.py` 的分界规则一个字不动：凡是要进常驻层、要被滑块吃、要被导出拿走的像素仍来自真解码。为此
`measures.decoded_from` 必须是 `"camera_preview"` 并进事件——RAW 的糊度读数属于相机预览而不属于母档，
这件事要看得见。`allow_preview` 的全仓两处开启点（`session.make_thumb`、`server._pick_measure_one`）都写在
`decode.py` 顶部注释里，第三处不许开。

## 3. 拒绝掉的备选

- **下一份开源"闭眼/美学"分类器**：不可审计的权重 + 单独许可追踪 + 与离线最净依赖冲突；而且 DoD 要的正是
  不许拿它冒充能力。
- **把这三条 if 叫「AI 智能挑图」**：伪装 AI，明令禁止。
- **只做 UI 层的假徽章**（前端按缩略图亮度自己判）：读数双出处，且屏幕上的结论无法复算——与假滤镜同类。
- **只按绝对能量判糊**：实测会把压暗 0.35× 的图冤枉成糊图（0.001417 < 0.005476）。
- **阈值取在替身与睁开的空档里**：夹具是画的脸，那样等于给真人小眼睛发"闭眼"标签。

## 4. 验证

- `engine/tests/test_pick.py` 21 条：dHash 方向性、分组闭包与措辞边界、清晰度两格与平坦护栏、批内相对线、
  曝光裁切的方向不对称（暗≠死黑）、量纲回归（三种画布同一几何都读回画进去的比值）、取小值、契约不足返 None、
  `eyes_unknown` 不写睁眼、每条原因带 method/value/threshold、人工标记优先、三档移动判界线、指纹随阈值变、
  序列化带来源。
- `engine/tests/test_acceptance_p1.py::test_pick_...`（端到端，真引擎子进程 + 真 mediapipe）：五张已知方向的
  输入 → 近似组、糊、过曝、疑似闭眼各按方向标出；判据指纹等于 ready 那份；**两次跑读数逐字节相同**；
  被拒的三种非法命令不留半截状态；跑完前后目录名单与逐文件 sha256 完全相同；加人工标签后 `overridden_by_user`
  为真而读数原样；`session_state.docs[].pick` 带着徽章要读的字段。
- `engine/tests/test_pick.py::test_m0_env_bridge_returns_every_key_the_frontend_declares`（第 21 条，本轮
  真撞出来的）：宿主 `m0_env` 返回的键名单与前端 `M0Env` 声明**双向**比对。第一次跑第 7 臂时窗口等满
  900 s 也没出 `M0_PICK_RESULT`——TS 声明了 `auto_pick` 而 Rust 那份 `json!` 少返回这一格，`if
  (env.auto_pick)` 永远为假，TS 与 cargo 两边都全绿。JSON 边界上没有类型，这一类缺陷只能靠名单比对抓。
  变异自查做在归档里：把那行删掉，守卫精确报 `['auto_pick']`。
- `packaging/pick-calibrate.py`（已提交的标定台）：所有阈值的小数都能从它的输出里对回去。
- `packaging/m5-release-check.sh` 第 7 臂（`LRT_AUTO_PICK`，输入由 `packaging/make-test-pick-set.py` 确定性生成）：
  穿过 `runPick → Rust pick → 引擎 pick_* → 宿主 status.pick → DOM 徽章` 那四层，并核对装机件里
  ready 指纹 == 事件指纹、原因里没有"删"、sha256 台账前后一致。这一臂在 1.6.0 上抓出两格真缺陷，
  都记在这里而不是只留在 commit log 里，因为它们都是**任何一层编译期都抓不到**的那一类：
  ① 宿主 `m0_env` 少返回 `auto_pick` 那一格（前端臂永远点不着，而 TS/cargo 全绿）；
  ② 整条自动序列挂在 `LRT_AUTO_BENCH` 那道门上，少传它就是一段**静默 return**——脚本只能等满
     900 s 拿到一句"没跑完"。修法是两处都改成会自己报：前端过不了门就发 `M0_ERROR` 并列出挂了
     哪些臂；脚本先等 `M0_RELEASE`（60 s）再等臂，门上失败只记一条红，不重复计账。
     这条纪律适用于后面每一臂：**没有"读不到就跳过"，也没有"等不到就说是超时"**。

## 5. 诚实边界（这一版没做的）

不判人脸朝向/主体/构图美感/美学评分；不做跨图同一人（PORTRAIT-005）；不自动删除、不自动标记、不自动进回收站；
不学习用户偏好；`eyes_closed` 只在探得到脸时给出，多人图把所有脸一起量取最小值而不逐人报告。
手册里那"10 种场景分类"没有对应实现，因此 UI 上也就不出现对应承诺。
