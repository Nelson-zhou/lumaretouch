# Lens focus UI module: authored, runtime acceptance UNRUN

Requirement: `LNX-REF-WF-165438-165adae6a7`.

Reference: [PixCake official lens-blur guide](https://www.pixcakeai.com/guide/165438), read 2026-10-24. Its workflow includes analysis, five aperture-style choices, subject/click focus and a focus interval, depth visualization, clear/blur brushing, and apply/cancel. This module independently implements a review contract for that interaction family. It does not claim proprietary algorithm equivalence, batch parity, optical simulation, actual focal length or an f-number.

## What exists, and what does not

Owned implementation lives only in `ui/src/lensBlur/`. `index.ts` exports a host-owned workflow, a React review surface, exact versioned contracts, and geometry/image helpers. No shared application entry point, transport, native bridge, engine router, history owner, optional-model package, repository configuration or saved recipe is modified here.

The UI is substantive but is **not an end-to-end integrated feature** by itself. The host must supply an actual current-source image, source-bound depth samples (or an explicitly requested and separately labeled manual editing plane), a verified capability report, a non-mutating preview service, and the existing document/history transaction owner. No fake engine, fabricated measured depth, generated photograph, hardcoded model readiness or successful receipt is shipped in production files.

The interface begins unavailable, requires `port.protocol === 2`, and independently requires an authoritative v1 `LensCapability` for `lnx.lens_blur.v1`. All command, review and receipt envelopes use v2. The operation, recipe, depth and capability formats remain v1; the context keeps its existing exact unversioned shape. V1 wire envelopes fail closed, rather than silently receiving new save semantics. This is an authored source-contract evolution, not a claim that a deployed client was migrated. A model adapter being installed does not establish native renderer availability or successful depth inference. A renderer being installed does not establish a depth model.

## Stable host lifecycle

1. Create `createLensBlurWorkflow(port, options)` in the application owner, not inside a transient dialog. Its `submit` and `receipt` ports must use the existing durable transaction/receipt owner. Keep that owner across navigation, panel unmount, module disable and document switch. Supply `options.onTerminal` for an actual read-only editor refresh using the verified receipt and original command; an applied receipt targets `result_document_id`, not the original owner.
2. Call `setCapability` with the actual versioned renderer report. Unknown fields, unsupported operation/version, an available report with no kernels, or unavailable-with-kernels all fail closed. Disabling/replacing capability revokes candidate review but preserves the local recipe and all outstanding writes. This is an ordinary module boundary, not hot-loaded executable plugins.
3. Call `setContext` with a complete exact `LensContext`. The controller validates current document ID, document epoch, decimal revision, source content hash/dimensions/orientation, current-source PNG, depth provenance and depth raster. It copies accepted input before asynchronous verification. No depth defaults to `null`; pending/missing/error states must not carry a stale asset as though it were ready.
4. Render `LensBlurWorkspace` with that persistent workflow and `onExit`. A valid source PNG must pass SHA-256/PNG structure/CRC checks and then load at its declared natural size before controls activate. Both candidate PNGs independently pass the same integrity checks and their own load acknowledgement before the final checkbox can enable Apply.
5. Preview must be read-only with respect to the document and history. Return exact owner, request, session, candidate token, echoed recipe, authoritative recipe digest and `result_source_sha256` with actual full-frame before/after renders. The result digest is the canonical full-resolution candidate asset identity, not the after-PNG digest. A source-thumbnail copy, UI-generated blur, diagram, stale candidate or unrelated URL is not a preview substitute. The UI accepts only bounded inline RGB/RGBA PNG bytes, never arbitrary fetched URLs.
6. The “保存为新副本” action sends exactly one token-bound v2 Apply request with `return_mode: 'new_image'`, exact recipe/before/after/result-source digests and explicit reviewed acknowledgement. The host revalidates all identities and images and calls the existing `CreativeHost.commit_return` new-image boundary. It creates a distinct source-row document, leaves the original document and original file untouched, and returns verified new-document evidence. It does not append an original-document history entry. This creates an in-project copy, not an exported image file or an automatic project save. UI notifications never append history or manufacture success.
7. Cancel fences the whole `session_id`, including previews that finish late, and discards only temporary candidates. It must never roll back an already applied or unknown request. The host owns bounded candidate leases and cleanup for read-only previews replaced by newer context/review or invalidated during asynchronous verification. The UI ignores late preview results and cannot resurrect them.
8. A matching terminal applied/cancelled result becomes eligible for automatic `onExit` only after `onTerminal` finishes successfully. One session is one review/edit lifetime; a new editing session requires a new `session_id`. Context updates during terminal refresh are ignored, so the editor refresh cannot silently reopen the lens panel for the new copy before exit. A pending/unknown write permits only lookup of the same original command. A timeout, transport exception, malformed reply, missing new-document/output proof, source switch or failed lookup never authorizes resubmission or an assertion that no copy was created. Native status APIs must query the original write, not report merely that the status-query request succeeded.
9. Panel unmount calls `releasePresentation`: it revokes image/checkbox acknowledgement but keeps the command and receipt owner. Reopening requires fresh presentation. The application must not throw away the workflow/receipt ledger to bypass unresolved state. Terminal refresh has a separate state from the known commit outcome. On failure, keep `terminal_receipt` and offer only `refreshTerminal()` to repeat the read-only callback, never Apply/Cancel. Without a configured refresh callback, report `not-configured` and do not auto-exit or claim the editor refreshed. Manual return to the editor remains available after the terminal outcome is known.

Capability changes retain the current local recipe. Persisted project/history recipes remain owned by the shared host and must not be rewritten, reset or deleted merely because this UI, a native kernel or a model is missing. Neutral radius is explicitly zero; it is not equivalent to deleting a stored recipe. Unsupported future versions must remain intact and read-only upstream.

## Exact v2 new-copy write contract

Apply keys are exactly `version`, `action`, `request_id`, `session_id`, `owner`, `token`, `recipe_sha256`, `before_sha256`, `after_sha256`, `reviewed`, `return_mode`, `result_source_sha256`. `version` is 2; `action` is `apply`; `reviewed` is true; `return_mode` is `new_image`. The result hash is echoed from the reviewed candidate and participates in `lensReviewKey`, so changing it revokes the old image/checkbox acknowledgement. Cancel remains an exact six-key command (`version`, `action`, `request_id`, `session_id`, `owner`, `token`) with version 2 and a nullable candidate token.

Every receipt has exact identity/status keys: `version`, `request_id`, `session_id`, `action`, `owner`, `token`, `phase`, `outcome_unknown`, `message`. Pending/unknown receipts add nothing and require `outcome_unknown: true`. Terminal rejected/cancelled receipts add only `outcome`; cancelled is valid only for the original Cancel command. Applied terminal receipts add exactly `outcome`, `recipe_sha256`, `before_sha256`, `after_sha256`, `return_mode`, `copied_original_document_id`, `result_document_id`, `result_revision`, `result_source_sha256`, `no_change`.

Applied receipts must echo all reviewed digests and mode; the copied-original ID must equal `command.owner.document_id`; the result ID must be a distinct valid token. `result_revision` is the actual new source-row revision read back after commit, encoded as a bounded uint64 decimal string. It is not compared with the original revision and is not assumed to be zero: the creative-layer document starts at revision 0, while the canonical host fences the new source row separately (currently ordinarily revision 1). `result_source_sha256` must equal the reviewed canonical output digest, not the PNG hash. `no_change` means canonical pixel identity only: it must agree with result/source asset identity, and even a neutral candidate still creates a distinct independent copy. `document_revision`, `history_entry_id`, alternate return modes and all extra/missing fields are rejected. A legacy same-document/history receipt never proves a new copy was created.

The host must construct result fields from the actual canonical candidate and actual post-commit source row. Browser schema matching is correlation, not independent proof of native execution or file persistence. The UI neither invents a revision/history ID nor opens a second transaction path.

## Source and real depth contract

`LensOwner` binds `document_id`, `document_epoch`, `document_revision` and the immutable `source` tuple (`sha256`, `width`, `height`, `exif_normalized_once`). A different virtual/creative source is a different owner even if a thumbnail looks similar. The v1 source/recipe format remains source-only: no cropped proxies, display screenshot sampling or silent geometry reprojection. Hosts with incompatible downstream geometry must refuse capability for that context rather than widening this mapping.

Depth is `version: 1`, a server token, exact owner, `near-zero-far-one`, `normalized_full_frame_pixel_centres`, EXIF-normalized orientation, and a bounded full-frame `u16-le` raster. `raster.width/height` are the actual supplied processing/display-sample resolution, not source dimensions copied into metadata. SHA-256 covers the exact little-endian bytes. Base64 must be canonical and match precisely `width * height * 2` decoded bytes. The browser hashes and decodes those bytes and paints the visualization from them; no spatial gradient is used as depth. Color mapping is yellow near / purple far; focus-range highlighting is a display transform only.

An upstream float32 depth adapter may retain its full-precision processing output. To provide this compact UI asset, the host must explicitly encode the same whole-frame relative depth as `round(clamp(value,0,1) * 65535)`, hash the resulting bytes and preserve the exact source and processing dimensions. If resizing is necessary, the adapter/host owns and documents that conversion. Do not report invented original processing dimensions. Subject or confidence information must never be inferred from a depth map alone.

Provenance is an exact union:

- `model`: model ID, pinned model SHA-256, and actual inference ID. This says that the host supplied a model-derived result for this source; it does not claim benchmark accuracy, physical depth or all-model readiness.
- `manual`: `user_supplied_depth`, explicitly labeled “手动深度输入，不是 AI 分析”. An actual user-provided depth raster is required. A manually marked subject polygon, segmentation mask, guessed horizon or synthetic gradient must not be silently substituted.
- `manual`: `user_defined_plane`, with an explicit constant `depth_value` and `acknowledgement_id`. This is a separately disclosed **manual editing baseline**, not measured or estimated scene depth. The optional `port.prepareManualPlane` is called only by the explicit “人工散焦编辑（不做 AI 景深分析）” action. The UI sends owner/session/request identity, value 0.5 and `acknowledged_manual: true`. The returned complete context must preserve the exact owner/session/source PNG and return matching provenance/acknowledgement. The browser verifies that every supplied sample equals the declared quantized constant. The UI never synthesizes these bytes itself and never starts this path automatically. It labels the visualization as a constant editing plane, switches to blur painting and explains that signed clear/blur strokes provide manual defocus control. This remains a partial manual path, not delivery of the official AI depth-analysis requirement.

Subject focus is disabled unless the model-derived asset includes an explicit near/far interval and a measured subject-mask hash. Both manual provenance types are ineligible. The UI never manufactures a subject from the image centre or a foreground-depth percentile. That upstream subject proof is not produced by this module.

## Geometry, brush semantics and kernel mapping

Source points store normalized **pixel centres**. For source size `W × H`, source-centre coordinates are `x = u*(W-1)`, `y = v*(H-1)`. The displayed rectangle covers pixel edges from `-.5` to `W-.5` and `-.5` to `H-.5`. Pointer-to-source conversion maps display edge fractions to `fraction*W-.5`, then clamps only to the nearest valid source centre. Letterbox padding is rejected by the exported fitted-rectangle helper. The component itself displays an uncropped source-aspect rectangle and uses the SVG viewBox `-.5 -.5 W H`.

Source centre `x` maps to depth centre `(x+.5)*depthWidth/W-.5` (and likewise Y). Bilinear sampling clamps only at the depth-raster border. This differs from both source-edge normalized masks and naïve `u*(depthWidth-1)` sampling. Point focus samples actual decoded depth. A first click on the initial all-depth interval makes a local 0.10-wide relative interval, clipped at the ends; subsequent clicks retain its current half-width. Sliders directly set near/far and switch the mode to interval.

The five honest kernel strings map in order to native numeric aperture codes 0–4:

1. `circular_disk`
2. `rim_weighted_disk`
3. `regular_pentagon`
4. `regular_octagon`
5. `cat_eye_intersection`

`max_radius_px` is explicit source-pixel radius in [0,128], not a physical lens parameter. Focus resolves upstream to `focus_near/focus_far`; `depth_falloff`, `occlusion_tolerance`, and `rotation_radians` map directly to the isolated native settings. No proprietary “Circle II” equivalence is claimed.

The browser does not calculate a request/recipe JSON hash. `recipe_sha256` is an authoritative host candidate digest, returned with a token and echoed unchanged on Apply. The browser compares the complete returned recipe to the requested values independently. Host hashing must bind its own canonical parsed candidate to the token; it must not assume Python JSON reserialization has identical float bytes to JavaScript. PNG/depth hashes cover binary bytes and do not have that ambiguity.

Refinement strokes carry unique IDs, clear/blur mode, unit amount/flow/feather, radius as a fraction of the source short edge, and source-centre points. The full recipe binds every stroke to source + depth token/hash/provenance. The host rasterizes them once into the native signed plane: clear toward -1; blur toward +1. The shared host defines deterministic flow/feather compositing and must preserve stroke ordering. This UI does not fake the numeric refinement result. Its cyan/orange overlay is explicitly a coverage annotation, not feathered output. Pointer cancellation, source switches, module disable, tool changes and over-budget strokes discard only the unfinished stroke; existing strokes remain. No silent thinning or point truncation is permitted.
